## Acceptance #2 — machine-scope VM verification

Windows 11 Pro 25H2 (26200.9168), elevated (`win-11-vm\randy`), self-contained
`otw.exe`. Each entry: `otw apply --only <id> --no-restore-point --json`, an
independent native read (`Get-ItemProperty` / `Get-CimInstance Win32_Service` /
`Get-ScheduledTask` / `Get-WindowsOptionalFeature` / `Get-MpPreference`), then
`otw revert <runId> --json` and a second independent read. The CLI's own detection
is never the evidence. Full per-entry transcript:
[M4/machine-scope-verification.md](M4/machine-scope-verification.md).

Of the **340** Basic/Balanced entries, **190** were exercisable over the headless
SSH session; **150** were deferred (below). Of the 190 exercised, **144 are now
`Verified`**:

| Outcome | Count | Handling |
| --- | --- | --- |
| Verified — full round-trip (apply → desired → revert → pre-state) | 131 | status → Verified |
| Verified — already-compliant on 25H2 (target already in the desired state) | 13 | status → Verified (no-op, noted in the evidence log) |
| Not applicable on this image (component absent, or edition-gated to Ent/Edu) | 16 | left Draft |

### Why the 46 exercised-but-not-Verified entries were not verified

- **19 failed.** 14 are Microsoft Defender / ASR entries whose `Set-MpPreference`
  writes are blocked by **Tamper Protection** (confirmed `IsTamperProtected=True`
  on the VM): the write silently no-ops and the engine correctly fails
  verification rather than claiming success. 2 target **TrustedInstaller-owned
  registry keys** (`…\CurrentVersion\Communications`,
  `…\Windows Search\Gather\…\SystemIndex`) that deny writes even when elevated —
  apply legitimately rolls back. 1 is a `powercfg /hibernate /type reduced` that
  the VM's hibernate configuration rejects. 2 are Local-GPO writes that never won
  the `registry.pol` lock (see below).
- **16 not applicable.** The target service / task / optional feature is absent on
  this 25H2 image (already removed by Windows), or the entry is `appliesTo`
  Enterprise/Education only and correctly no-ops on Pro. These are correct
  outcomes, not defects; they need an image that actually has the component.
- **8 anomalies.** Mostly Local-GPO **revert contention** — the entry applied
  correctly (independent read = desired) but the automated revert hit the
  `registry.pol` lock; the same revert path round-trips cleanly for the 100+
  policy entries that passed. One (`security.media.dma-disable-under-lock`) is a
  genuine **scan-compliance discrepancy** worth follow-up: the engine reports the
  entry compliant while the value is absent.
- **3 managed.** Detected as Group-Policy-managed and skipped — an artifact of
  Local-GPO residue accumulated by the per-entry batch itself, not an entry
  defect.

## Deviations (honest, and why)

- **150 of 340 Basic/Balanced entries were not exercisable over the headless SSH
  session** and remain `Draft`:
  - **75 per-user (`User`-hive) entries** — the interactive-user resolver returns
    `null` over headless SSH (the M3 limitation), so per-user writes are safely
    refused; a console-session fallback is M5 work.
  - **47 network / remote-access / authentication entries** (firewall inbound
    block, RDP/WinRM/SMB, remote-registry, LSA / credential-guard, audit policy) —
    applying these even briefly can sever the SSH session used for automation, so
    they are deferred to a console-session run, not verified blind over SSH.
  - **28 Appx removals** — removal is intentionally not round-trip reversible by
    the tool (reinstall is out-of-band via the Store / each entry's
    `reinstallHint`), so the apply → revert → equals-pre model does not apply.
- **Product findings surfaced by verification** (candidate hardening, recorded in
  PLAN.md): the engine does not retry the Local-GPO `registry.pol` lock
  (`0x80070020`) that separate elevated invocations contend on; Defender/ASR
  configuration via `Set-MpPreference` is blocked by Tamper Protection and would
  need a GPO/Intune path; a Policy write over an OS-default key deletes rather
  than restores the original value on revert; one scan-compliance discrepancy.
- **Mutation gate DEFERRED** (Stryker/MTP, stryker-net#3094).

## Fixes made during M4 verification

- `otw updates resume` now clears **every** active pause, not just the latest
  (stacked-pause bug); regression test + `MutableTimeProvider`.
- `otw scan|apply --only <id>` no longer requires `--profile` (the per-entry
  verification path); `--profile` is required only in profile mode.
