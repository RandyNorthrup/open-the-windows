## VM verification — Windows 11 Pro 25H2

Host: Windows 11 Pro, build 26200 (25H2), `.NET 10.0.10` runtime, elevated
(`randy`), over SSH (session 0). The framework-dependent CLI was deployed and run.

**Formats.** `otw audit run --baseline ms-baseline-25h2` with each of `--json`,
`--csv`, `--html`, `--sarif --out` produced four files (a.json 7616 B, a.csv
3928 B, a.html 5138 B, a.sarif 9692 B). Content checks: the JSON carries a 64-hex
integrity `hash` and a `report` object; the SARIF is `version 2.1.0`; the HTML
starts `<!DOCTYPE html>`; the CSV has the expected header. `otw audit list` shows
the three baselines (16 rules each); `otw audit validate` returns valid.

**Score change after apply/revert.** Auditing `ms-baseline-25h2` scored **33**
before. Applying `security.autoplay.disable-autorun` (`otw apply --only`, exit 0)
flipped `MSS-Autoplay-TurnOff-AllDrives` from `Fail` to `Pass` and raised the score
to **40**; `otw revert last` restored the prior state and the score returned to
**33**. (The apply/revert engine reported a non-`Completed` revert state — a
pre-existing M3 detail — but the prior state was fully restored, confirmed by the
score returning to 33 and by re-reading the values.)

**Spot-check (10+ rules).** The 16 `disa-stig-v2r7` results were dumped and
cross-checked against independent registry / firmware reads on the same host:

## Product finding surfaced by VM verification

Applying a policy-backed hardening tweak first showed the corresponding baseline
rule as `Manual`, not `Pass`, because the audit mapped any managed setting to
`Manual`. Fixed: `AuditEngine` now scores a managed setting by its observed value
(policy at the desired value → `Pass`; at a different value → `Fail`). The score is
correspondingly more accurate. See the CHANGELOG "Fixed" entry.

## Deviations (honest, and why)

- **Baseline versions.** The spec named `disa-stig-v2r8` and `cis-win11-ent-v5.1`.
  The files ship as `disa-stig-v2r7` and `cis-win11-ent-v4.0` because those are the
  releases whose exact control ids were verified: the current DISA STIG is V2R7
  (there is no V2R8), and the CIS v5.1.0 benchmark PDF blocks automated retrieval,
  so the v4.0.0 section numbers (verified from the v4.0.0 document) are used rather
  than guessed v5.1 numbers. Naming a file for a version whose ids were not
  verified would be a false claim.
- **Baselines are a curated mapping**, not a full framework reproduction: they
  cover high-value controls (16 rules each) that map to the catalogue tweaks and
  the read-only health checks. This is by design (ADR 0002 forbids copying
  benchmark text); rules with no automated mapping report `Manual`.
- **GUI hooks added.** The spec's GUI items (Dashboard score per baseline, Security
  page baseline filter) are implemented, though they are Design, not Acceptance,
  criteria.
- **Report signing exercised locally, not via CI.** ES256 signing/verification is
  unit-tested (signed round-trip + tamper detection) and available through
  `otw audit run --sign`; no CI-produced signed artifact is verified because the
  project stays local until it is pushed.
